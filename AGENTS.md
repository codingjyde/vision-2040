# Rhema Nigeria Vision 2040 Repository

## Purpose

This repository contains the official working knowledge for the Rhema Nigeria Vision 2040 programme.

Treat this repository as organisational infrastructure rather than a collection of documents.

Its purpose is to preserve, develop, and communicate the organisational knowledge required to fulfil Vision 2040.

The repository may contain:

- Vision documents
- Strategic plans
- PMO artefacts
- Governance frameworks
- Leadership guides
- Operating models
- Playbooks
- Policies
- SOPs
- Checklists
- Templates
- Training materials
- Budget frameworks
- KPI frameworks
- Communications resources
- Research
- Meeting papers
- Decision records
- Reference material

Every contribution should strengthen the repository as a whole.

# Repository Philosophy

The repository is a single body of knowledge.

Documents are not independent.

Every document contributes to one coherent organisational operating system.

Whenever modifying one document, consider the impact on the entire repository.

Prefer consistency over convenience.

# Core Context

Rhema Nigeria exists as a vital extension of the mandate given to Kenneth E. Hagin in 1950 to "Go teach my people faith."

Vision 2040 exists to prepare Rhema Nigeria for long-term multiplication through healthy leadership, sound governance, excellent training, effective ministry systems, and sustainable expansion.

The 2026–2027 programme is a restructuring phase.

Its purpose is to build systems before scaling.

Expansion begins after validated operating models exist.

# Repository Consistency

This repository should never contain conflicting guidance without the user's knowledge.

Before modifying or creating a document, consider whether the change would:

- contradict another document;
- redefine an established term;
- alter organisational philosophy;
- change governance;
- change responsibilities;
- invalidate templates;
- introduce competing frameworks;
- duplicate existing guidance.

If a conflict exists:

STOP.

Do not silently continue.

Instead:

1. Explain the conflict.
2. Identify affected documents.
3. Explain the consequences.
4. Recommend solutions.
5. Wait for user direction.

# Breaking Changes

Treat major documentation changes as breaking changes.

Examples include:

- renaming workstreams;
- changing organisational structures;
- redefining KPIs;
- changing governance models;
- changing document templates;
- changing terminology.

Before making breaking changes:

- identify affected documents;
- explain downstream impact;
- recommend an update plan;
- wait for approval.

# Document Versioning

Unless instructed otherwise, every significant document is version controlled.

## Initial Version

Every new document begins at:

1.0.0

## Working Revisions

Routine improvements increase the patch version.

Example:

1.0.0

1.0.1

1.0.2

Patch revisions include:

- clarification
- wording
- formatting
- examples
- corrections
- non-breaking improvements

## Releases

Only the user authorises releases.

Examples:

1.0.x → 1.1.0

1.1.x → 1.2.0

Do not release documents automatically.

## Major Versions

Increment the major version only after significant redesign.

Example:

1.x.x → 2.0.0

Major versions require user approval.

## Status

Each document should include a status.

# Writing Style

Use British English.

Write clearly.

Prefer short paragraphs.

Prefer active voice.

Use practical language.

Avoid corporate jargon.

Avoid unnecessary adjectives.

Avoid em dashes.

Write documents that busy leaders can understand quickly.

---

# Markdown Standards

Use clean Markdown.

Keep headings consistent.

Use tables only when they improve clarity.

Use numbered lists for sequences.

Use bullet lists for grouped ideas.

Avoid unnecessary formatting.

---

# Quality Standard

Every document should be:

- clear
- practical
- internally consistent
- well structured
- reusable
- durable

Documents should remain useful years after they are written.

---

# Final Review

Before completing any task, ask:

Does this strengthen the repository?

Is it consistent with existing documents?

Have I introduced unnecessary duplication?

Should another document also be updated?

Have I preserved the repository's single source of truth?

Would this still make sense five years from now?

If any answer is uncertain, raise the issue with the user before proceeding.
